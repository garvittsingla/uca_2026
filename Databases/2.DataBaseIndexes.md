1. What Is an Index?

An index is a separate data structure maintained by the database to make data retrieval faster.

A standard MySQL B-Tree index keeps values in an ordered structure so the database can locate matching rows without scanning the entire table.

For example:

CREATE INDEX idx_email
ON Employee(email);

Now a query like:

SELECT *
FROM Employee
WHERE email = 'aarav@company.com';

can potentially find the row much faster than scanning the entire table.

Primary purpose

Speed up data retrieval.

Indexes are especially useful for columns frequently used in:

WHERE
JOIN
ORDER BY
GROUP BY
2. Why Do We Need Indexes?

Imagine a table with 1,000,000 rows.

Without an appropriate index:

SELECT *
FROM Employee
WHERE email = 'aarav@company.com';

MySQL may need to check many rows.

This is called a:

Full Table Scan

With:

CREATE INDEX idx_email
ON Employee(email);

MySQL can use the index to locate the required value much more efficiently.

Simple idea
Without index:

Row 1 → check
Row 2 → check
Row 3 → check
...
Row 1,000,000 → check

With index:

          Index
            ↓
      Find matching value
            ↓
        Required row
3. Index Trade-Off

Indexes improve read performance, but they have costs.

Operation	Effect
SELECT	Usually faster
INSERT	Can become slower
UPDATE	Can become slower
DELETE	Can become slower
Storage	More space required

Why?

When data changes, the database must also maintain the indexes.

For example, if a table has:

5 indexes

and you insert a row, the database may need to update all relevant index structures.

Remember

Indexes optimize reads but add overhead to writes.

4. Selectivity

Selectivity describes how well a column can distinguish between rows.

High selectivity

A column has many distinct values.

Example:

email
user_id
phone_number

Suppose:

10 rows
10 different email addresses

This is highly selective.

An index is usually very useful.

Low selectivity

A column has relatively few distinct values.

Example:

department
gender
status

Suppose:

10 rows
3 departments

For example:

Engineering
Engineering
Engineering
Engineering
HR
HR
HR
Sales
Sales
Sales

The department column has low selectivity.

If the query:

SELECT *
FROM Employee
WHERE department = 'Engineering';

matches many rows, MySQL may decide that using the index is not worthwhile.

It may instead perform a:

Full Table Scan
Important

Having an index does not guarantee that MySQL will use it.

The query optimizer decides which execution plan is estimated to be cheaper.

5. Composite Indexes

A composite index contains multiple columns.

Example:

CREATE INDEX idx_dept_salary
ON Employee(department, salary);

This index has the order:

department → salary

department is the leading column.

salary is the second column.

The order matters.

6. Leftmost-Prefix Rule

Suppose we have:

INDEX(a, b, c)

The index can generally be used most effectively for:

a
a + b
a + b + c

But not generally for:

b
c

because the leading column a has been skipped.

Example

Index:

CREATE INDEX idx_dept_salary
ON Employee(department, salary);

This query can use the index efficiently:

SELECT *
FROM Employee
WHERE department = 'Engineering';

because:

Index:
department → salary
↑
Used

But:

SELECT *
FROM Employee
WHERE salary > 70000;

does not generally get the same efficient B-Tree lookup because:

Index:
department → salary
              ↑
            Used

department was skipped
Mental model

Think of a composite index like a dictionary sorted by:

Last Name → First Name

You can efficiently search by last name.

But searching only by first name doesn't let you directly jump to the correct location because the data is primarily organized by last name.

7. Using Both Columns

Consider:

CREATE INDEX idx_dept_salary
ON Employee(department, salary);

Query:

SELECT *
FROM Employee
WHERE department = 'Engineering'
  AND salary > 90000;

This is a good use of the composite index.

Conceptually:

department = Engineering
        ↓
Find Engineering section
        ↓
salary > 90000
        ↓
Find matching salaries
Important

The order in the WHERE clause does not determine the index order.

These express the same filtering conditions:

WHERE department = 'Engineering'
  AND salary > 90000;

and:

WHERE salary > 90000
  AND department = 'Engineering';

The index itself is still:

(department, salary)
8. EXPLAIN

MySQL provides EXPLAIN to show how it plans to execute a query.

Example:

EXPLAIN
SELECT *
FROM Employee
WHERE department = 'Engineering';

Important columns include:

Column	Meaning
type	How MySQL accesses the table
key	Index MySQL chose
rows	Estimated rows examined
Extra	Additional execution information
key

The key column tells you which index MySQL actually chose.

Example:

key: idx_email

means:

MySQL chose idx_email

If:

key: NULL

then MySQL did not choose an index for that table access.

9. Full Table Scan

If EXPLAIN shows:

type = ALL
key  = NULL

this generally means:

MySQL is performing a full table scan and did not choose an index.

Conceptually:

Table
 ↓
Row 1
Row 2
Row 3
Row 4
...
Row N

Every row may need to be examined.

Important

A full table scan is not automatically bad.

For a tiny table, scanning the entire table may actually be cheaper than using an index.

The optimizer makes the decision based on its cost estimates.

10. Covering Index

A covering index contains all the columns needed to answer a query.

Example:

CREATE INDEX idx_dept_salary
ON Employee(department, salary);

Query:

SELECT department, salary
FROM Employee
WHERE department = 'Engineering';

The index already contains:

department
salary

Therefore MySQL may be able to answer the query using only the index without fetching the full table rows.

In EXPLAIN, the Extra column may show:

Using index
Remember

Using index often indicates that the query can be satisfied from the index itself.

11. LIKE and Indexes

Standard B-Tree indexes work well when MySQL knows the beginning/prefix of the value.

Index-friendly
WHERE name LIKE 'Sha%'

MySQL knows that matching values start with:

Sha

So it can perform an efficient prefix/range lookup.

Similarly:

WHERE name LIKE 'Sh%'

can use the known prefix:

Sh

An exact match is also index-friendly:

WHERE name LIKE 'Sharma'
Leading %

Consider:

WHERE name LIKE '%arma'

The database does not know the starting characters.

It only knows that the value ends with:

arma

A standard B-Tree index generally cannot efficiently perform the lookup based on that suffix.

Rule
LIKE 'abc%'     → ✅ Generally index-friendly

LIKE 'ab%'      → ✅ Generally index-friendly

LIKE 'abc'      → ✅ Exact lookup

LIKE '%abc'     → ❌ Generally not efficiently searchable
Easy rule to memorize

Leading % = B-Tree index generally cannot efficiently search the prefix.

12. Indexes and Sorting

Indexes can sometimes help with sorting.

For example, an index on:

salary

can potentially help a query involving:

ORDER BY salary

But an index on email does not directly optimize:

SELECT *
FROM Employee
ORDER BY salary;

because:

Index → email

Query → salary

The indexed column and required ordering do not match.

13. When an Index May Not Help

An index can exist but still not be used.

Common reasons:

1. Wrong column

Index:

INDEX(email)

Query:

WHERE department = 'Sales'

The index does not help with the department condition.

2. Skipping the leading column

Index:

INDEX(department, salary)

Query:

WHERE salary > 70000

The leading column department is skipped.

3. Low selectivity

If a condition matches a large percentage of the table, MySQL may decide:

Index lookup + many row accesses

is more expensive than:

Full table scan
4. Leading wildcard
WHERE email LIKE '%company.com'

A standard B-Tree index generally cannot efficiently use the suffix as the starting point.

5. Very small table

For a tiny table, scanning all rows may be cheaper than using an index.

Answer:

Speed up data retrieval.

✅ Good candidate for the composite index.

The index MySQL actually chose.

Question: What does key = NULL mean?

Question: What is the downside of many indexes?

More storage and slower INSERT, UPDATE, and DELETE operations due to index maintenance.

17. Final Mental Model

Whenever you see an indexing question, ask:

Step 1 — What is the index?
INDEX(a, b)
Step 2 — What is the leading column?
a
Step 3 — Does the query use a?

If yes → the index may be useful.

If it only uses b → the composite index generally cannot provide the same efficient leftmost lookup.

Step 4 — How selective is the condition?

Highly selective → index is often more attractive.

Low selective → full scan may be cheaper.

Step 5 — Is there a wildcard?
LIKE 'abc%'

Usually good.

LIKE '%abc'

Usually not efficient with a standard B-Tree.

Step 6 — Check EXPLAIN

     +

Think through it:

   ↓
   Yes

2. Is department the leading column?
   ↓
   Yes

3. Is salary also in the index?
   ↓
   Yes

4. Does the query use both?
   ↓
   Yes

5. Are all selected columns in the index?
   ↓
   Yes

   ↓
   Yes

   ↓

Final Summary

An index is a data structure that helps the database find data faster.

The most important concepts are:

Indexes speed up reads.
Indexes add storage and write overhead.
Selectivity affects whether an index is worthwhile.
Composite index order matters.
The leftmost/leading column is critical.
EXPLAIN key tells you which index was chosen.
type = ALL usually means a full table scan.
key = NULL means no index was chosen.
Using index can indicate a covering/index-only access.
LIKE 'abc%' can generally use a B-Tree prefix lookup.
LIKE '%abc' generally cannot efficiently use a standard B-Tree index.
More indexes are not always better.
🧠 Golden Rule

Indexes make finding data faster, but they are not free. The database optimizer decides whether using an index is actually cheaper than scanning the table.
